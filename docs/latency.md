# Задержка генерации со слиянием адаптера и без (`eval/latency.py`)

**Модуль:** `src/kanlora/eval/latency.py`
**Тесты:** `tests/eval/test_latency.py`

## Зачем нужна отдельная метрика, которой нет в задании

LoRA и DoRA после обучения складываются с весами основы: поправка
`delta_W` вычисляется один раз при слиянии, и на инференсе метод не стоит
ничего дополнительного по сравнению с исходной моделью. KAN-LoRA
нелинейна по построению (`delta_W(x) = B * phi(A x)`, см.
[`adapters.md`](adapters.md)) — поправка зависит от входа, и её нельзя
свернуть в один тензор весов. `KANLoRALinear.can_merge` поэтому всегда
`False`, а `merge()` наследует `AdapterLinear.merge()` и бросает
`NotImplementedError`. Это цена, которую спецификация сравнения не
называет явно (метрики качества и видеопамять её не отражают), но она
существенна для вывода вида «нелинейность стоит X% к задержке генерации»
на защите. Здесь эта цена измеряется числом.

## `merge_adapters`

```python
def merge_adapters(model: torch.nn.Module) -> int
```

Проходит по `adapter_modules(model)` (единый перечислитель адаптеров,
`docs/adapters.md`) и для каждого вызывает `module.merge()`, подставляя
результат — обычный `nn.Linear` с поглощённой поправкой — на место
адаптера тем же способом, что и `inject_adapters` (поиск родителя по
`name.rpartition(".")` и `setattr`). Возвращает число заменённых модулей.

На KAN-LoRA `module.merge()` бросает `NotImplementedError` — функция это
не перехватывает и не оборачивает: отказ слиться является свойством
метода, а не технической накладкой, которую стоит прятать за собственным
типом исключения.

Слияние обязано быть тождественным преобразованием выхода модели: до и
после `merge_adapters` модель обязана возвращать одни и те же логиты на
одном и том же входе, иначе замер задержки без слияния сравнивал бы одну
модель, а замер со слиянием — другую, отличающуюся ещё и по качеству.

## `LatencyReport` и `measure_latency`

```python
@dataclass(frozen=True)
class LatencyReport:
    seconds_per_token: float
    total_seconds: float
    tokens: int
    merged: bool

@torch.inference_mode()
def measure_latency(
    model, tokenizer, prompt: str, *,
    device: torch.device,
    max_new_tokens: int = 64,
    repeats: int = 3,
    warmup: int = 1,
    merged: bool = False,
) -> LatencyReport
```

Измеряет среднее время жадной генерации фиксированного числа токенов:

1. `model.to(device)`, `model.eval()`, промпт кодируется один раз и без
   специальных токенов (`add_special_tokens=False`) — так же, как в
   `collate.encode` на обучении и в `generate_sql` на оценке.
2. `warmup` прогревочных вызовов `model.generate(...)` **до** старта
   секундомера — первый вызов CUDA включает выделение памяти и подбор
   ядер, и без прогрева замер мерил бы разогрев рантайма, а не сам метод.
3. `repeats` засекаемых вызовов, время делится на `repeats` — среднее,
   а не медиана и не минимум, как в остальных замерах проекта.
4. `max_new_tokens == min_new_tokens` во всех вызовах: число
   сгенерированных токенов зафиксировано, генерация не останавливается
   по `eos` раньше срока, поэтому `seconds_per_token` сопоставимо между
   вызовами и между методами.
5. `torch.cuda.synchronize()` до и после засекаемого участка, только на
   `device.type == "cuda"` — без синхронизации замер CUDA-времени через
   `time.perf_counter()` считал бы лишь время постановки ядер в очередь,
   а не их выполнения; на CPU синхронизация не нужна и не вызывается.

Поле `merged` в `LatencyReport` не вычисляется функцией — вызывающий код
передаёт его явно, отражая, был ли перед замером вызван `merge_adapters`.
Само измерение агностично к тому, слит адаптер или нет: оно просто мерит
время генерации текущей модели.

Декоратор `@torch.inference_mode()` — как и в `eval/generate.py`
(`docs/generate.md`) — отключает автоград на всей функции; здесь это не
только экономия памяти, но и часть корректности замера: обратный проход
не должен ни выполняться, ни искажать время инференса.

## Проверенные инварианты

- `merge_adapters` заменяет каждый из адаптеров (LoRA, DoRA) обычным
  `nn.Linear` и возвращает их число; после слияния `adapter_modules`
  возвращает пустой список
  (`test_merging_replaces_adapters_with_plain_linear`, LoRA и DoRA).
- Слияние не меняет логиты модели на случайном батче токенов при
  случайно инициализированных весах адаптера
  (`test_merging_does_not_change_the_output`, LoRA и DoRA).
- На KAN-LoRA `merge_adapters` пробрасывает `NotImplementedError`, а не
  молча пропускает нелинейный адаптер
  (`test_kan_lora_refuses_to_merge`).
- `measure_latency` (помечен `@pytest.mark.slow`, гоняет настоящую
  генерацию на `tiny_causal_lm`/`tiny_tokenizer` из `tests/conftest.py`,
  см. `docs/generate.md`) возвращает ровно запрошенное число токенов,
  положительное суммарное время и `seconds_per_token ==
  total_seconds / tokens` (`test_latency_report_is_filled`).
- Промпт замера кодируется без специальных токенов, как на обучении и
  оценке: в модель уходит ровно посимвольная кодировка строки без BOS
  (`test_latency_prompt_is_tokenized_without_special_tokens`).

## Замер в каждом прогоне

`scripts/run_experiment.py` (`nonlinearity_and_latency`,
`docs/experiment-runner.md`) мерит задержку в каждом прогоне и пишет её в
поле `latency` карточки: `seconds_per_token`, `total_seconds`, `tokens`,
`merged`, `device`. Главная таблица (`docs/make-tables.md`) показывает
столбец «Задержка без слияния, мс/токен».

- Промпт — первый промпт отложенной выборки, один и тот же у всех
  методов.
- `config.max_new_tokens` токенов, 3 повтора, 1 прогрев (значения по
  умолчанию `measure_latency`).
- Замер идёт без слияния адаптера (`merged: false`). У LoRA и DoRA после
  слияния задержка равна задержке базовой модели, то есть строке `none`
  главной таблицы; KAN-LoRA не сливается в принципе, и её число — как
  раз цена нелинейности.
- Замер идёт после индекса нелинейности. Генерация замера проходит через
  адаптеры KAN-LoRA и расширяет их `observed_range`; индекс же должен
  считаться по размаху, накопленному за обучение, валидацию и оценку.
  Обратный порядок молча изменил бы индекс
  (`test_latency_is_measured_after_nonlinearity`).
- Числа сравнимы только на одном устройстве: рядом с ними в карточке
  лежит `latency.device`.

## Почему DoRA без слияния заметно медленнее LoRA

На смок-прогоне (CPU, `configs/smoke.yaml`) задержка DoRA без слияния
516.0 мс/токен против 46.6 у LoRA и 53.8 у `none`, то есть примерно в 11
раз выше LoRA. Это следует из прямого прохода `DoRALinear`
(`src/kanlora/adapters/dora.py`): `forward` на каждом вызове строит
`effective_weight()` — считает направление `W + s · B A`, норму его строк
(`direction.norm(dim=1)`, отсоединённую от графа) и нормированный вес
`m · direction / norm`, и только потом применяет `F.linear`. Пересчёт идёт
над всей матрицей d_out×d_in, а не над активацией: произведение `B A`
стоит порядка `r · d_in · d_out` операций (в LoRA поправка считается
через активацию, `r · (d_in + d_out)` на токен), и ещё несколько
проходов по матрице (сложение с `W`, норма, деление). При декодировании
одного токена основная работа — матричное умножение на `d_in · d_out`, и
пересчёт веса оказывается дороже его примерно на порядок при `r = 8`.

На обучении та же добавка размазана по длинным последовательностям (вес
пересчитывается раз на проход, а не на токен), поэтому DoRA там медленнее
LoRA лишь примерно вдвое (8.8 против 4.3 мин на смоке). После слияния
(`merge_adapters`) вес `effective_weight()` вычислен один раз и заменён
обычным `nn.Linear`, поэтому слитая DoRA идёт со скоростью строки `none`.
Именно поэтому столбец главной таблицы подписан «без слияния»: для
LoRA и DoRA это не цена метода на инференсе, а цена неслитой формы.
Числа смока — только процессорные; реальные дают прогоны на GPU.
