# Промпт, токенизация и маска функции потерь (`collate.py`)

**Модуль:** `src/kanlora/data/collate.py`
**Тесты:** `tests/data/test_collate.py`

## Зачем это отдельный модуль

Соединяет `Text2SqlExample` и `DatabaseSchema` (`docs/data.md`) с тем, что
реально уходит в модель: строкой промпта, списком `input_ids` и списком
`labels` для функции потерь. Ошибка здесь — самая коварная во всём проекте:
если промпт не замаскирован, обучение не падает, функция потерь исправно
убывает, метрики считаются, но модель учится предсказывать текст схемы базы
данных, а не SQL-запрос. Внешне прогон выглядит рабочим. Поэтому маска
проверяется тестами напрямую, по значениям `labels`, а не косвенно — через
качество генерации.

## Промпт (`PROMPT_TEMPLATE`, `build_prompt`)

```python
PROMPT_TEMPLATE = "Database schema:\n{schema}\n\nQuestion: {question}\n\nSQL:\n"
```

`build_prompt(question, schema_text) -> str` подставляет вопрос и уже
сериализованную схему (`serialize_schema` из `schema.py`) в этот шаблон.
Рамка промпта — английские служебные слова (`Database schema`, `Question`,
`SQL`) — одна и та же для Spider (вопросы на английском) и для PAUQ (вопросы
на русском): меняется только содержимое `{question}`, само оформление
промпта нет. Это намеренно: различие между наборами в экспериментах должно
сводиться к языку вопроса, а не привноситься дополнительно другим
оформлением промпта, что обесценило бы сравнение результатов на Spider и
PAUQ.

`build_prompts(examples, schemas) -> list[str]` — применяет `build_prompt` к
списку примеров, беря схему каждого примера по `example.db_id`; порядок
результата совпадает с порядком `examples`.

## Токенизация и маска (`encode`)

```python
def encode(tokenizer, prompt: str, target: str, max_length: int) -> dict[str, list[int]]
```

Раздельно токенизирует промпт и целевой SQL-запрос (`add_special_tokens=False`
— рамку токенов строит сам модуль, а не токенизатор), затем:

1. К токенам цели дописывается `tokenizer.eos_token_id`. Без конца
   последовательности жадная генерация на этапе оценки не имеет причины
   остановиться и будет генерировать до `max_new_tokens`.
2. Если токенов цели (вместе с EOS) больше, чем `max_length`, функция роняет
   `ValueError` с сообщением, содержащим «не помещается». Тихо обрезать
   часть SQL-запроса нельзя: это незаметно испортило бы обучающую пару —
   целевая строка перестала бы быть тем запросом, который есть в данных, и
   ошибка не проявилась бы нигде, кроме итогового качества.
3. Промпт **усекается по голове**, если суммарная длина превышает
   `max_length`: `room = max_length - len(target_ids)`,
   `prompt_ids = prompt_ids[-room:]`. Отрезается начало схемы/вопроса, а не
   конец, потому что конец промпта (`"...\n\nSQL:\n"`) — сигнал модели о том,
   что пора генерировать запрос; отрезать его означало бы разрушить формат
   промпта на длинных примерах.
4. `labels` формируются из промпта и цели той же длины, что и `input_ids`:
   позиции промпта заполнены `IGNORE_INDEX`, позиции цели (SQL плюс EOS)
   содержат те же id, что и `input_ids` на этих позициях. `IGNORE_INDEX = -100`
   — значение, которое `torch.nn.CrossEntropyLoss` по умолчанию игнорирует
   при вычислении функции потерь.

Результат — словарь `{"input_ids": list[int], "labels": list[int]}` без
паддинга; паддингом занимается `Collator` на уровне батча, а не `encode` на
уровне одного примера.

## Сборка датасета (`build_dataset`)

```python
def build_dataset(examples, schemas, tokenizer, max_length) -> tuple[list[dict], int]
```

Строит промпты через `build_prompts`, затем для каждой пары
(промпт, пример) вызывает `encode` и параллельно считает число усечённых
примеров. Пример считается усечённым, если сумма длины промпта и длины цели
(SQL плюс EOS) **до** урезания превышает `max_length` — то есть по тому же
условию, по которому `encode` фактически обрезает голову промпта, а не
косвенно, через сравнение длин после кодирования. Эта величина идёт в
карточку результата эксперимента: если усечённых примеров много, часть схем
или вопросов не доехала до модели целиком, и это способно повлиять на
метрику сильнее, чем выбор метода адаптации, — то есть это надо суметь
предъявить и объяснить на защите, а не обнаружить постфактум по аномальному
качеству.

Первая черновая реализация метода из плана считала усечения по разнице длин
`input_ids` уже после урезания, с мёртвой веткой `if ... : pass` — рабочей,
но запутанной. От неё отказались в пользу прямого сравнения
`prompt_length + target_length > max_length` до урезания: то же самое
условие, что фактически определяет отрезание головы промпта внутри `encode`,
только явно.

## Сборка батча (`Collator`)

```python
class Collator:
    def __init__(self, pad_token_id: int) -> None: ...
    def __call__(self, batch: Sequence[dict[str, list[int]]]) -> dict[str, torch.Tensor]: ...
```

Дополняет все примеры батча справа до длины самого длинного примера в этом
же батче (динамический паддинг, не до глобального `max_length`):

- `input_ids` дополняется `pad_token_id`;
- `attention_mask` дополняется нулём — паддинг исключается из внимания;
- `labels` дополняется `IGNORE_INDEX` — паддинг исключается из функции
  потерь тем же механизмом, что и токены промпта.

Возвращает тензоры `torch.long`, готовые к прямому проходу модели без
дополнительных преобразований.

## Проверенные инварианты

- Промпт содержит и схему, и вопрос, и заканчивается на `"SQL:\n"`
  (`test_prompt_contains_schema_and_question`).
- Рамка промпта совпадает для русского и английского вопроса при замене
  вопроса на заглушку (`test_prompt_frame_is_identical_for_both_datasets`).
- Токены промпта в `labels` — `IGNORE_INDEX`, токены цели — нет
  (`test_labels_mask_the_prompt`).
- `labels` и `input_ids` одной длины, а на позициях цели совпадают
  (`test_labels_align_with_input_ids`).
- Последовательность заканчивается на `eos_token_id` и в `input_ids`, и в
  `labels` (`test_sequence_ends_with_eos`).
- При переполнении обрезается голова промпта, а цель (вместе с EOS) остаётся
  в конце последовательности целиком
  (`test_truncation_cuts_the_prompt_and_keeps_the_target`).
- Цель, которая сама по себе не помещается в `max_length`, роняет
  `ValueError` с сообщением «не помещается»
  (`test_target_longer_than_limit_raises`).
- `build_dataset` возвращает по одному закодированному примеру на входной
  пример и верно считает число усечённых
  (`test_build_dataset_reports_truncations`).
- Порядок `build_prompts` совпадает с порядком входных примеров
  (`test_build_prompts_matches_dataset_order`).
- `Collator` дополняет справа, маскирует паддинг в `attention_mask` и
  `labels`, возвращает `torch.long`
  (`test_collator_pads_inputs_and_masks_padding`).

## Не реализовано

- Само превращение результата `Collator` в обучающий цикл (оптимизатор,
  накопление градиента, обрезание нормы градиента, чекпоинтинг) — задача 10
  и задача 11 плана, ещё не сделаны.
- Выбор конкретных значений `max_length` и токенизатора для экспериментов
  фиксируется конфигурацией прогона (задача 16 плана), а не этим модулем:
  `collate.py` параметричен по `max_length` и принимает любой совместимый
  токенизатор.
