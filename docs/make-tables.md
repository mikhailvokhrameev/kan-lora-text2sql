# Сборка таблиц и графиков (`scripts/make_tables.py`)

**Модуль:** `scripts/make_tables.py`
**Тесты:** `tests/test_make_tables.py`

## Зачем таблицы собираются скриптом, а не пишутся руками

Единица поставки экспериментов — карточка результата (`docs/experiment-
runner.md`, `results/*.json`). Если числа в тексте работы переносить в
таблицы руками, любое число становится невосстановимым из карточек: нельзя
проверить, откуда оно взялось, и легко ошибиться при копировании. Скрипт
читает все карточки из каталога и одной командой строит `results/tables.md`
и `results/figures/fraction_inside_grid.png` — заново, целиком, при каждом
запуске.

## `load_cards`

```python
def load_cards(directory: Path) -> list[dict]
```

Читает все файлы `*.json` из каталога (сортировка по имени файла — для
воспроизводимого порядка строк в таблицах) и разбирает их как JSON. Формат
карточки не проверяется схемой — он зафиксирован в `results.py`
(`build_result_card`), и здесь предполагается уже валидным.

## `aggregate`

```python
def cell_key(card: dict) -> tuple[str, str, str | None, bool | None]
def aggregate(cards: list[dict]) -> dict[tuple[str, str, str | None, bool | None], dict[str, tuple[float, float] | None]]
```

Группирует карточки по ключу `(method, dataset, optimizer, learn_input_scale)`
(его строит `cell_key`) и для каждой метрики даёт пару `(среднее, размах)` по
зёрнам.

Ключ содержит всё, что отличает конфигурацию, кроме зерна. Прогон с Muon и
абляция `--no-input-scale` — другие эксперименты; при ключе `(method, dataset)`
они молча усреднялись бы с основным прогоном AdamW, и размах по «зёрнам»
включал бы разницу между конфигурациями. `learn_input_scale` различает только
`kan_lora` (так же, как суффикс `-no-input-scale` в `run_id`,
`config.py`): у LoRA и DoRA поле не используется, и для них в ключе всегда
значение по умолчанию.

У базовой модели без адаптера (`method: none`, `docs/experiment-runner.md`)
ключ — `("none", dataset, None, None)`: обучения не было, оптимизатора и
масштаба входа нет. Этот случай разбирается первым, до чтения
`config.optimizer.name`, — иначе секция `optimizer`, которая в замороженной
конфигурации базовой модели всё равно есть, подставила бы `adamw`
(`test_baseline_cell_key_has_no_optimizer_and_no_input_scale`).

Значения читаются из карточки: оптимизатор — из `optimizer`, затем из
`config.optimizer.name`. Верхнее поле карточки `optimizer` — источник
истины, `config.optimizer.name` — запасной вариант для карточек без этого
поля; `run_experiment` пишет оба из одной конфигурации, так что расходиться
они не могут. `learn_input_scale` — из `config.adapter`. Старые
карточки без этих полей читаются как значения конфигурации по умолчанию
(`adamw`, `learn_input_scale = true`, `configs/base.yaml`), поэтому ранее
собранные результаты агрегируются по-прежнему
(`test_old_cards_without_optimizer_fields_count_as_defaults`).

Размах (`max - min`), а не стандартное отклонение — при трёх зёрнах (0, 1, 2
из глобальных ограничений плана) оценка отклонения статистически
неустойчива, а размах прямо отвечает на вопрос «насколько далеко разъезжаются
прогоны одного метода». Выводы в тексте работы формулируются только по
различиям, выходящим за этот размах: ожидаемая разница между методами по
Exact Match — порядка одного-двух процентов, то есть внутри разброса по
случайному зерну.

Значения `None` (не число) исключаются из усреднения до деления, а не
заменяются нулём: Execution Accuracy на PAUQ может быть `null` при
отсутствии файлов баз данных (`docs/execution.md`), и «не мерили» обязано
остаться отличимым от «получили ноль». Если после фильтрации не осталось ни
одного значения, ячейка получает `None` целиком, а не `(0.0, 0.0)`.

Помимо метрик (`exact_match`, `execution_accuracy`) в тот же агрегат
попадают `peak_memory_bytes`, `trainable_parameters` и
`seconds_per_token` (из `card["latency"]`, у старых карточек без поля —
`None`) — они нужны основной
таблице, а по построению карточки одинаковы для всех зёрен одного метода на
одном наборе, поэтому их среднее и размах не публикуются отдельно. У
карточек `method: none` оба поля `null` и, как и отсутствующая метрика,
дают `None` для всего ключа (поля читаются через `card.get`).

## `main_table`

```python
def main_table(cards: list[dict]) -> str
```

Строит таблицу Markdown: одна строка на ключ агрегации
`(метод, набор, оптимизатор, learn_input_scale)`. Строки базового уровня
(`method: none`) идут первыми, остальные — лексикографически по ключу, как
и раньше (`_row_order`). Столбцы: метод, оптимизатор, набор и далее
метрики; последний столбец — «Задержка, мс/токен»: среднее по зёрнам
`latency.seconds_per_token`, умноженное на 1000, или «—», если ни у одной
карточки ключа поля нет (старые карточки). Числа сравнимы только между
прогонами на одном устройстве (`latency.device`, `docs/latency.md`).
У абляции без обучаемого масштаба входа подпись метода получает суффикс
«(без масштаба входа)». Метод, оптимизатор и набор выводятся значениями
конфигурации (`lora`, `dora`, `kan_lora`, `adamw`, `muon`, `spider`, `pauq`)
без перевода в
«красивые» подписи — таблица собирается из тех же строк, что и `run_id`
карточек, и не вносит собственного словаря соответствий, который расходился
бы с конфигурацией при добавлении нового метода.

Строка «без адаптера (базовый уровень)» обязательна методологически: без
базового уровня (модель без адаптера) невозможно ответить на вопрос «что
дала адаптация вообще», а не только «какой из трёх методов адаптации
лучше». Она собирается из карточек `method: none`
(`scripts/run_experiment.py --method none`) так же, как строки методов, —
по одной на набор, со средним и размахом по зёрнам, если базовая модель
прогонялась с несколькими зёрнами (генерация жадная, так что размах
ожидается нулевым). Столбец оптимизатора — «—»; пик видеопамяти и число
обучаемых параметров в карточке `null` (обучения не было) и в таблице тоже
«—» (`test_baseline_row_is_filled_from_cards`,
`test_baseline_rows_per_dataset`). Пока ни одной карточки `method: none`
нет, на этом месте стоит строка «без адаптера (базовый уровень) | — | — |
нет прогона | нет прогона | — | — | —», чтобы пропуск базовой точки был виден
в таблице (`test_main_table_includes_the_baseline_row_placeholder`).

Каждая ячейка метрики выводится функцией `_cell` в виде `среднее ± размах/2`
(например, `0.4200 ± 0.0200`) или строкой «не измерялась», если для этого
ключа агрегации ни одно зерно не дало значения.

## `nonlinearity_table` и `optimizer_table`

```python
def nonlinearity_table(cards: list[dict]) -> str
def optimizer_table(cards: list[dict]) -> str
```

В отличие от `main_table` (единственной таблицы, агрегирующей по зёрнам,
поэтому ключ `cell_key` нужен только ей), обе таблицы построены по отдельным прогонам
(`run_id`), а не агрегированы по зерну — они раскрывают величины, которые
имеет смысл смотреть по каждому прогону отдельно, а не усреднять.

`nonlinearity_table` берёт `spline_stats` карточки (сводка
`analysis/spline_stats.py`, `docs/nonlinearity.md`) и для каждого прогона
выводит:

- среднее по адаптерам модели индекса нелинейности слоя `index` — доли
  суммарной дисперсии рёбер слоя, которую не объясняют прямые (ΣRSS/ΣTSS);
- максимум этого индекса по адаптерам;
- последнее значение `fraction_inside_grid` (среднее за последнюю эпоху) —
  долю активаций сплайна внутри сетки к концу обучения.

Карточки без `spline_stats` (LoRA, DoRA — они не нелинейны, поле равно
`null`) пропускаются, а не выводятся строкой из прочерков.

Адаптеры, у которых `index` равен `NaN` (все активации вне сетки, измерять
нечего — см. `docs/nonlinearity.md`), при агрегации пропускаются: среднее и
максимум считаются только по измеренным адаптерам, иначе `NaN` заражал бы
среднее, а `max()` с `NaN` зависит от порядка элементов. Так же
пропускаются адаптеры без ключа `index`: это карточки старого формата
(`mean`/`max` по рёбрам), с новыми несравнимые. Если не измерен ни один
адаптер прогона, в обеих ячейках стоит «не измерялась» — как и для
отсутствующей метрики в основной таблице. Покрывают это
`test_nonlinearity_table_skips_unmeasured_adapters`,
`test_nonlinearity_table_marks_run_with_nothing_measured` и
`test_nonlinearity_table_does_not_read_old_card_format`.

Карточки базовой модели (`method: none`) в обе таблицы не попадают: у них
нет `spline_stats` (как у LoRA/DoRA) и нет оптимизатора — `optimizer_table`
пропускает их явно, а не выводит строкой нулей
(`test_baseline_is_absent_from_the_optimizer_and_nonlinearity_tables`).
График `plot_fraction_inside_grid` пропускает их, потому что
`fraction_inside_grid` у них `null` (`test_plot_tolerates_baseline_cards`).

`optimizer_table` берёт `optimizer_coverage` карточки — распределение
обучаемых параметров между `torch.optim.AdamW` и `torch.optim.Muon`
(`docs/optimizers.md`) — и выводит абсолютные числа и долю параметров,
пришедшихся на Muon. При нулевом суммарном числе параметров в обоих
оптимизаторах (не должно происходить на реальных карточках, но карточка не
проверяется схемой на входе) строка выводится с нулями и прочерком в доле,
без деления на ноль.

Ветка «сумма параметров равна нулю» оформлена как обычный `if total: ... else:
...` на двух строках, а не как тернарное выражение внутри f-строки. Более
компактная запись через тернарное выражение здесь читается неоднозначно:
условие `if total else` синтаксически привязывается к результату всего
`f"..."`, а не к числителю доли, из-за чего вся строка целиком (включая уже
подставленные `muon` и `adamw`) выглядит так, будто зависит от `total`, хотя
фактически заменяется только последний столбец.

## `plot_fraction_inside_grid`

```python
def plot_fraction_inside_grid(cards: list[dict], path: Path) -> None
```

Строит график `fraction_inside_grid` по эпохам, по одной линии на прогон, у
которого это поле не пусто (для LoRA и DoRA список пуст — линия не рисуется).
Ось Y ограничена `[0.0, 1.05]`: величина по определению не превышает 1.0, а
небольшой отступ сверху не даёт точкам у значения 1.0 сливаться с верхней
рамкой графика. Легенда добавляется только если на графике есть хотя бы одна
линия — на пустом входе `plt.legend()` печатает предупреждение в лог без
дополнительной проверки.

Рисование идёт через backend `Agg` (`matplotlib.use("Agg")` до импорта
`pyplot`), заданный до первого импорта `matplotlib.pyplot` — без этого на
машине без дисплея (в том числе в CI и на машине обучения без X11) выбор
интерактивного backend по умолчанию может завершиться ошибкой при попытке
открыть окно.

## `main` и формат вывода

```python
def main() -> int
```

Аргументы командной строки: `--results` (каталог с карточками, по умолчанию
`results`) и `--output` (каталог для `tables.md` и `figures/`, по умолчанию
тот же `results`). Если каталог с карточками пуст, скрипт печатает сообщение
и возвращает код 1, не создавая пустых `tables.md` — таблица без единой
строки была бы легко спутана с таблицей, которая просто не пересобрана после
изменений.

При наличии карточек в `results/tables.md` последовательно пишутся три
раздела — основная матрица, нелинейность, покрытие Muon — и создаётся
`results/figures/fraction_inside_grid.png`. Оба пути создаются заново при
каждом запуске (`Path.mkdir(parents=True, exist_ok=True)`), а не
дозаписываются: файл `tables.md` — не журнал, а снимок текущего набора
карточек.

## Проверенные инварианты

- `load_cards` читает ровно те карточки, что лежат в каталоге, независимо от
  числа файлов (`test_loads_every_card`).
- `aggregate` даёт среднее и размах по зёрнам, совпадающие с ручным расчётом
  на трёх карточках одного метода (`test_aggregate_reports_mean_and_spread`);
  для единственного зерна размах равен нулю
  (`test_single_seed_has_zero_spread`).
- Карточки AdamW и Muon, а также KAN-LoRA с обучаемым и фиксированным
  масштабом входа не смешиваются
  (`test_aggregate_does_not_mix_optimizers`,
  `test_aggregate_does_not_mix_input_scale_ablation`); флаг масштаба входа не
  расщепляет LoRA/DoRA (`test_input_scale_flag_does_not_split_non_kan_methods`);
  строки основной таблицы подписаны оптимизатором и абляцией
  (`test_main_table_labels_rows_by_optimizer_and_input_scale`).
- Отсутствующая Execution Accuracy (`None`) не превращается в ноль при
  усреднении, а даёт `None` целиком для всего ключа агрегации
  (`test_absent_execution_accuracy_does_not_become_zero`).
- `main_table` показывает размах рядом со средним (символ `±`), включает
  обе сравниваемые в тесте строки (метод, набор) и является таблицей Markdown,
  а не текстом без разметки (`test_main_table_shows_spread_next_to_the_mean`),
  и всегда содержит строку базового уровня без адаптера: из карточек
  `method: none`, если они есть, иначе строку «нет прогона»
  (`test_main_table_includes_the_baseline_row_placeholder`,
  `test_baseline_row_is_filled_from_cards`, `test_baseline_rows_per_dataset`).
- Ключ агрегации базовой модели — `(none, набор, None, None)`, её карточки не
  попадают в таблицы нелинейности и покрытия Muon, а график их переносит
  (`test_baseline_cell_key_has_no_optimizer_and_no_input_scale`,
  `test_baseline_is_absent_from_the_optimizer_and_nonlinearity_tables`,
  `test_plot_tolerates_baseline_cards`).
- `optimizer_table` показывает покрытие и Muon, и AdamW
  (`test_optimizer_table_shows_muon_coverage`).
- `plot_fraction_inside_grid` создаёт непустой файл графика
  (`test_plot_writes_a_file`).
- Главная таблица показывает задержку генерации в мс/токен: среднее по
  зёрнам `latency.seconds_per_token`, умноженное на 1000
  (`test_main_table_shows_generation_latency`); у карточек без поля
  `latency` (старые) в столбце прочерк, а не падение
  (`test_main_table_marks_missing_latency`).

## Не реализовано

Карточки базовой модели без адаптера (`method: none`) код уже производит,
но сами прогоны базовой модели на Spider и PAUQ ещё не выполнены. Замер фактического
времени прогона и запуск полной матрицы экспериментов на GTX 1080 Ti (задача
19 плана) — ещё не сделаны; до них `results/*.json` пусты и
`python scripts/make_tables.py` возвращает код 1.
