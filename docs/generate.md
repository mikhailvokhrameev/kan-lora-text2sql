# Генерация SQL (`eval/generate.py`)

**Модуль:** `src/kanlora/eval/generate.py`
**Тесты:** `tests/eval/test_generate.py`

## Зачем генерация жадная и одна на все прогоны

`generate_sql()` — единственная функция генерации, которой пользуются все три
метода адаптации на этапе оценки. Отбор всегда жадный (`do_sample=False`,
`num_beams=1`): семплирование с температурой добавило бы к метрикам Exact
Match и Execution Accuracy случайность сверх той, что уже вносят три
зафиксированных зерна обучения, и небольшая разница между LoRA, DoRA и
KAN-LoRA утонула бы в шуме генерации.

## `normalize_sql`

```python
def normalize_sql(text: str) -> str
```

Обрезает сгенерированный текст по первому переводу строки или первой точке с
запятой и схлопывает произвольные пробелы в один. Модель при жадной генерации
охотно продолжает текст дальше собственного ответа (например, пишет следующий
вопрос после запроса), а всё, что идёт после первого перевода строки или
`;`, к самому SQL-запросу не относится и должно быть отброшено до сравнения с
эталоном.

## `generate_sql`

```python
def generate_sql(
    model,
    tokenizer,
    prompts: list[str],
    *,
    device: torch.device,
    batch_size: int = 8,
    max_new_tokens: int = 128,
) -> list[str]
```

Пакетная жадная генерация под `torch.inference_mode()`. Порядок действий:

1. Модель переводится на `device`, в режим `eval()`, `model.config.use_cache
   = True` — генерация нуждается в кеше ключей/значений, в отличие от
   обучения с чекпоинтингом (`docs/train-loop.md`).
2. `tokenizer.padding_side` временно принудительно ставится в `"left"` и
   восстанавливается в исходное значение по выходу из функции (`finally`),
   даже при исключении.
3. Промпты режутся на пакеты по `batch_size`, каждый пакет кодируется с
   `padding=True` и подаётся в `model.generate(...)`.
4. Из выхода `generate` отрезается только продолженная часть
   (`output[:, encoded["input_ids"].shape[1]:]`) — сам промпт из ответа
   вырезается по числу токенов входа, а не по маркерам, что корректно
   работает вместе с дополнением слева.
5. Продолжение декодируется пакетно (`batch_decode`, `skip_special_tokens=
   True`) и прогоняется через `normalize_sql`.

**Почему дополнение обязано быть слева.** При генерации у causal-модели
следующий токен предсказывается по последней позиции последовательности.
Если дополнять справа, то у более коротких промптов в пакете последняя
позиция перед генерацией пришлась бы на токен-заполнитель, а не на конец
реального промпта, и модель продолжала бы заполнитель вместо вопроса.
Дополнение слева выравнивает конец всех промптов пакета на одну и ту же
позицию независимо от их длины.

## `TinyTokenizer` — фикстура для тестов без сети

Тесты `test_generates_one_string_per_prompt` и
`test_batching_does_not_change_the_result` помечены `@pytest.mark.slow` и
гоняют настоящий `generate_sql` на `tiny_causal_lm` (`tests/conftest.py`),
но без реального токенизатора Qwen2.5-Coder: его словарь (150k+ токенов) не
совместим со словарём фикстуры (`vocab_size=64`), а `AutoTokenizer.
from_pretrained` требует сети.

Вместо этого `tests/conftest.py` определяет фикстуру `tiny_tokenizer`
(класс `TinyTokenizer`) — посимвольный токенизатор с кодом символа по модулю
64, дополняющий слева и умеющий пакетно кодировать и декодировать список
строк через объект `transformers.BatchEncoding` (нужен ради метода `.to
(device)`, которым пользуется `generate_sql`). Это тот же принцип, что и у
`FakeTokenizer` в `tests/data/test_collate.py` (Задача 9,
`docs/collate.md`), но с батчами вместо одной строки за раз — фикстура
рассчитана на переиспользование в Задаче 17 (замер задержки генерации).

## Проверенные инварианты

- `normalize_sql` обрезает по первому переводу строки
  (`test_cuts_at_the_first_newline`), по первой точке с запятой
  (`test_cuts_at_the_semicolon`), схлопывает пробелы
  (`test_collapses_whitespace`) и не падает на пустой/пробельной строке
  (`test_empty_generation_stays_empty`).
- `generate_sql` возвращает ровно одну строку на каждый промпт
  (`test_generates_one_string_per_prompt`).
- Результат не зависит от размера батча: генерация по одному промпту за раз
  и генерация тем же набором промптов одним пакетом дают идентичный список
  строк (`test_batching_does_not_change_the_result`) — иначе метрики оценки
  зависели бы от технической настройки `batch_size`, не имеющей отношения к
  сравниваемым методам.

## Не реализовано

Сборка конфигурации и карточки результата прогона, замер задержки
генерации со слиянием адаптера и без — задачи 16–17 плана, ещё не сделаны.
`generate_sql` спроектирован под них: возвращает обычный список
нормализованных строк SQL в порядке промптов, без привязки к конкретной
метрике оценки. Официальная метрика Exact Match, Execution Accuracy и мера
выученной нелинейности реализованы — см. [`exact_match.md`](exact_match.md),
[`execution.md`](execution.md), [`nonlinearity.md`](nonlinearity.md).
