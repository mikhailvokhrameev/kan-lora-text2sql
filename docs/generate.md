# Генерация SQL (`eval/generate.py`)

**Модуль:** `src/kanlora/eval/generate.py`
**Тесты:** `tests/eval/test_generate.py`

## Зачем генерация жадная и одна на все прогоны

`generate_sql()` — единственная функция генерации, которой пользуются все три
метода адаптации на этапе оценки. Отбор всегда жадный (`do_sample=False`,
`num_beams=1`): семплирование с температурой добавило бы к метрикам Exact
Match и Execution Accuracy случайность сверх той, что уже вносят три
зафиксированных зерна обучения, и небольшая разница между LoRA, DoRA и
KAN-LoRA утонула бы в шуме генерации.

## `normalize_sql`

```python
def normalize_sql(text: str) -> str
```

Если в тексте есть Markdown-блок кода, сначала извлекает содержимое первого
блока (подраздел ниже). Обрезает сгенерированный текст по первому переводу
строки или первой точке с запятой и схлопывает произвольные пробелы в один.
Модель при жадной генерации охотно продолжает текст дальше собственного ответа (например, пишет следующий
вопрос после запроса), а всё, что идёт после первого перевода строки или
`;`, к самому SQL-запросу не относится и должно быть отброшено до сравнения с
эталоном.

Резка идёт посимвольно через внутренний хелпер `_cut_outside_quotes`, который
отслеживает, находится ли текущий символ внутри одинарной или двойной
кавычки (с поддержкой экранирования `\'`/`\"`), и обрезает по первому
`\n`/`;`, встреченному **вне** кавычек. Это важно, потому что валидный SQL
может содержать `;` или перевод строки прямо в строковом литерале
(`WHERE name = 'a;b'`) — наивная резка по первому вхождению символа в сыром
тексте обрезала бы такой запрос до знака препинания внутри значения, а не по
границе самого запроса. Символы внутри литерала при этом всё равно проходят
через последующее схлопывание пробелов (`_WHITESPACE.sub`), так что перевод
строки в значении станет пробелом, как и везде в результате.

### Извлечение SQL из Markdown-блока (решение протокола оценки)

Перед резкой `normalize_sql` ищет в тексте Markdown-блок кода — ограду
` ``` ` с необязательным тегом языка (` ```sql `, ` ``` `). Если блок есть,
дальше обрабатывается только содержимое **первого** блока (регулярное
выражение `_FENCED_BLOCK`): от конца строки с открывающей оградой до
закрывающей ограды, а если её нет (генерация оборвалась по
`max_new_tokens`), — до конца текста. Однострочная запись
` ```SELECT ...``` ` тоже распознаётся. Внутри блока текст режется только по
первой `;` вне кавычек, но не по переводу строки: границу ответа уже задала
ограда, а SQL в блоке модель обычно пишет в несколько строк
(`SELECT a\nFROM t`), и резка по первому `\n` оставила бы от запроса одну
строку. Затем, как и прежде, схлопываются пробелы. Если ограды в тексте нет,
поведение `normalize_sql` прежнее: резка по первому `\n` или `;` вне
кавычек.

Зачем это нужно. Instruct-модель без дообучения (базовая точка без
адаптера, `method: none`, `docs/experiment-runner.md`) обычно отвечает
пояснением и запросом в блоке ` ```sql `. Без извлечения резка по первому переводу строки
оставляла бы от такого ответа строку вроде `Here is the query:` или
` ```sql `, и Exact Match и Execution Accuracy базовой модели были бы
занижены до нуля из-за формата ответа, а не из-за качества SQL.

Правило применяется одинаково ко всем методам и к базовой модели:
`normalize_sql` вызывается внутри общей `generate_sql`, отдельной
ветки для базовой модели нет. Обученные адаптеры учатся на голом SQL без
ограды (`docs/collate.md`), поэтому на их ответы правило практически не
влияет; если такой ответ всё же содержит ограду, из него тоже берётся
содержимое блока. Это изменение протокола оценки: карточки, посчитанные до
него, могут отличаться от новых на ответах, где модель поставила ограду, и
для сравнения методов все прогоны должны считаться одной версией кода.

## `generate_sql`

```python
def generate_sql(
    model,
    tokenizer,
    prompts: list[str],
    *,
    device: torch.device,
    max_length: int,
    batch_size: int = 8,
    max_new_tokens: int = 128,
) -> list[str]
```

Пакетная жадная генерация под `torch.inference_mode()`. Порядок действий:

1. Если `max_length - max_new_tokens <= 0`, функция роняет `ValueError`:
   промпту не остаётся места.
2. Модель переводится на `device`, в режим `eval()`, `model.config.use_cache
   = True` — генерация нуждается в кеше ключей/значений, в отличие от
   обучения с чекпоинтингом (`docs/train-loop.md`).
3. Промпты режутся на пакеты по `batch_size`. Каждый промпт пакета
   токенизируется и усекается функцией `truncate_prompt` из
   `src/kanlora/data/collate.py` до бюджета `max_length - max_new_tokens`
   (раздел ниже).
4. Пакет дополняется слева `tokenizer.pad_token_id` до самого длинного
   промпта (`_pad_left`), `attention_mask` — нули на заполнителях, единицы
   на токенах промпта. Тензоры подаются в `model.generate(input_ids=...,
   attention_mask=...)`. Токенизатор сам пакет не дополняет, поэтому его
   `padding_side` не трогается.
5. Из выхода `generate` отрезается только продолженная часть
   (`output[:, input_ids.shape[1]:]`) — сам промпт из ответа вырезается по
   числу токенов входа, а не по маркерам, что корректно работает вместе с
   дополнением слева.
6. Продолжение декодируется пакетно (`batch_decode`, `skip_special_tokens=
   True`) и прогоняется через `normalize_sql`.

**Усечение промпта — то же, что при обучении.** Бюджет промпта на оценке —
`max_length - max_new_tokens`: вместе с самым длинным допустимым ответом
последовательность не выходит за ту же длину `max_length`, что и на
обучении, где бюджет промпта — `max_length` минус длина ответа с EOS.
Правило усечения общее — `truncate_prompt` (`docs/collate.md`): помещающийся
промпт не меняется, у непомещающегося режется голова схемы, а системная
реплика, вопрос и открытие ответа assistant сохраняются. Промпт
токенизируется с `add_special_tokens=False`, как в `encode`: иначе
токенизатор, добавляющий BOS (например, Llama-3), дал бы на оценке лишний
первый токен, которого при обучении не было. До шага 6 плана исправлений
генерация промпт не усекала и токенизировала с `add_special_tokens` по
умолчанию (`True`), так что длинные схемы модель на оценке видела не так, как
на обучении. В эксперименте `max_length` передаётся из той же конфигурации
(`config.max_length`), что и в `build_dataset` (`scripts/run_experiment.py`).
Число усечённых промптов на оценке отдельно не сообщается; в карточку
результата по-прежнему идёт число усечённых обучающих примеров
(`truncated_prompts`).

**Откуда промпты и где генерация останавливается.** `generate_sql`
принимает уже готовые строки промптов и сам их не строит. Строит их
`build_prompts` из `src/kanlora/data/collate.py` — та же функция
`build_prompt`, что и при обучении: шаблон диалога токенизатора
(`apply_chat_template`) с `add_generation_prompt=True`, то есть промпт
обрывается на `<|im_start|>assistant\n` (`docs/collate.md`). В эксперименте
это связывает `scripts/run_experiment.py`. Генерация останавливается на
`eos_token_id=tokenizer.eos_token_id`; у Qwen2.5-Instruct это `<|im_end|>`
(id 151645) — конец реплики, которым `encode` завершает ответ при обучении.
Явная передача `eos_token_id` заменяет список из `generation_config.json`
модели (`[151645, 151643]`, т. е. ещё и `<|endoftext|>`) одним
`<|im_end|>`. Сам `<|im_end|>` в ответ не попадает: `batch_decode` идёт с
`skip_special_tokens=True`.

**Почему дополнение обязано быть слева.** При генерации у causal-модели
следующий токен предсказывается по последней позиции последовательности.
Если дополнять справа, то у более коротких промптов в пакете последняя
позиция перед генерацией пришлась бы на токен-заполнитель, а не на конец
реального промпта, и модель продолжала бы заполнитель вместо вопроса.
Дополнение слева выравнивает конец всех промптов пакета на одну и ту же
позицию независимо от их длины.

## `TinyTokenizer` — фикстура для тестов без сети

Тесты `test_generates_one_string_per_prompt` и
`test_batching_does_not_change_the_result` помечены `@pytest.mark.slow` и
гоняют настоящий `generate_sql` на `tiny_causal_lm` (`tests/conftest.py`),
но без реального токенизатора Qwen2.5-Coder: его словарь (150k+ токенов) не
совместим со словарём фикстуры (`vocab_size=64`), а `AutoTokenizer.
from_pretrained` требует сети.

Вместо этого `tests/conftest.py` определяет фикстуру `tiny_tokenizer`
(класс `TinyTokenizer`) — посимвольный токенизатор с кодом символа по модулю
64. Одну строку он кодирует в словарь `{"input_ids": list[int]}`, как
настоящий токенизатор при `tokenizer(text, add_special_tokens=False)` (так
кодирует промпты `truncate_prompt`), список строк — в дополненный пакет
`transformers.BatchEncoding` (так кодирует промпт замер задержки,
`docs/latency.md`); умеет пакетно декодировать и строить промпт шаблоном
ChatML (`apply_chat_template`), как `FakeTokenizer` в
`tests/data/test_collate.py` (`docs/collate.md`).

## Проверенные инварианты

- `normalize_sql` обрезает по первому переводу строки
  (`test_cuts_at_the_first_newline`), по первой точке с запятой
  (`test_cuts_at_the_semicolon`), схлопывает пробелы
  (`test_collapses_whitespace`) и не падает на пустой/пробельной строке
  (`test_empty_generation_stays_empty`).
- Из ответа с Markdown-блоком берётся содержимое первого блока с тегом языка
  и без него, многострочный SQL внутри блока не режется по переводу строки
  (`test_extracts_sql_from_a_fenced_block_with_language_tag`,
  `test_extracts_sql_from_a_fenced_block_without_language_tag`,
  `test_takes_only_the_first_fenced_block`); незакрытый блок берётся до конца
  текста (`test_unclosed_fence_takes_the_rest_of_the_text`), однострочная
  ограда распознаётся (`test_inline_fence_on_one_line`); ответ без ограды
  обрабатывается как раньше (`test_unfenced_generation_is_unchanged`).
- Резка не срабатывает на `;` и переводе строки внутри одинарных
  (`test_does_not_cut_at_semicolon_inside_single_quoted_string`) и двойных
  (`test_does_not_cut_at_semicolon_inside_double_quoted_string`,
  `test_does_not_cut_at_newline_inside_quoted_string`) кавычек, а
  экранированная кавычка (`\'`) не закрывает строковый литерал раньше
  времени (`test_escaped_quote_does_not_end_the_string`).
- `generate_sql` передаёт в `model.generate` `eos_token_id` токенизатора и
  `do_sample=False` (`test_generation_stops_at_the_tokenizer_eos`, заглушка
  модели, без сети и без обучения).
- Длинный промпт получает на оценке ровно те же токены, что и в
  последовательности `encode` при обучении, когда бюджеты равны
  (`max_new_tokens` равно длине ответа с EOS), и это результат
  `truncate_prompt` (`test_long_prompt_gets_the_same_token_ids_at_train_and_eval`).
- Каждый промпт пакета усекается отдельно, затем пакет дополняется слева, с
  нулями в `attention_mask` на заполнителях
  (`test_eval_prompts_are_left_padded_after_truncation`).
- Промпт на оценке токенизируется без специальных токенов: токенизатор,
  добавляющий BOS, не даёт лишнего первого токена, и вход генерации
  совпадает с началом последовательности `encode`
  (`test_eval_prompt_is_tokenized_without_special_tokens`).
- `max_new_tokens >= max_length` роняет `ValueError`
  (`test_budget_must_leave_room_for_the_prompt`).
- `generate_sql` возвращает ровно одну строку на каждый промпт
  (`test_generates_one_string_per_prompt`).
- Результат не зависит от размера батча: генерация по одному промпту за раз
  и генерация тем же набором промптов одним пакетом дают идентичный список
  строк (`test_batching_does_not_change_the_result`) — иначе метрики оценки
  зависели бы от технической настройки `batch_size`, не имеющей отношения к
  сравниваемым методам.

## Не реализовано

`generate_sql` спроектирован так, что подходит и для оценки, и для замера
задержки: возвращает обычный список нормализованных строк SQL в порядке
промптов, без привязки к конкретной метрике. Официальная метрика Exact
Match, Execution Accuracy, мера выученной нелинейности, конфигурация и
карточка результата прогона и замер задержки генерации со слиянием
адаптера и без реализованы — см. [`exact_match.md`](exact_match.md),
[`execution.md`](execution.md), [`nonlinearity.md`](nonlinearity.md),
[`experiment-runner.md`](experiment-runner.md), [`latency.md`](latency.md).
