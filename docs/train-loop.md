# Цикл обучения и замер видеопамяти (`train/loop.py`, `train/memory.py`)

**Модули:** `src/kanlora/train/loop.py`, `src/kanlora/train/memory.py`
**Тесты:** `tests/train/test_loop.py`, `tests/train/test_memory.py`

## Зачем один цикл на все три метода

`train()` — единственная функция, которая обучает модель, независимо от того,
какой адаптер в неё внедрён (`inject_adapters` из `kanlora.adapters.inject`).
Причина та же, что и у единого внедрителя адаптеров и единой разводки по
оптимизаторам: если бы LoRA, DoRA и KAN-LoRA обучались разным кодом, различие
в реализации циклов просочилось бы в сравнение методов, не выдав ошибки.

Сходимость самого цикла юнит-тестом в общем виде не проверяется — вместо
этого используется **переобучение двадцати примеров**: функция потерь обязана
упасть почти до нуля (`test_overfits_twenty_examples`). Такой тест ловит
подавляющее большинство ошибок цикла — неверную маску, оторванный граф
градиентов, замороженные не те параметры — ни одна из которых не даёт
исключения сама по себе, а незаметно портит качество итоговой модели.

## `PeakMemoryTracker`

```python
class PeakMemoryTracker:
    def __init__(self, device: torch.device) -> None: ...
    def reset(self) -> None: ...
    def peak_bytes(self) -> int: ...
```

Обёртка над `torch.cuda.max_memory_allocated`. На CPU (`device.type != "cuda"`)
`reset()` — не-операция, а `peak_bytes()` всегда возвращает `0`: карточка
результата эксперимента тогда честно показывает, что замера не было, а не
подставляет случайное или нулевое значение по совпадению.

Величина сравнима между LoRA, DoRA и KAN-LoRA только при жёстко одинаковых
длине последовательности, размере батча и точности (fp32) для всех трёх —
замер вынесен одним общим куском кода намеренно, чтобы «удобная» правка под
один метод не разошлась незаметно с остальными.

## `TrainConfig` и `TrainReport`

```python
@dataclass(frozen=True)
class TrainConfig:
    epochs: int = 2
    batch_size: int = 1
    gradient_accumulation: int = 8
    seed: int = 0
    gradient_checkpointing: bool = True
    log_every: int = 20
```

Нормы обрезания градиента в `TrainConfig` намеренно нет — она хранится только
в `OptimizerConfig` (`train/optimizers.py`) и берётся циклом оттуда. Если бы
одно и то же значение можно было задать в двух местах, они могли бы разойтись
молча и незаметно изменить методологию для части прогонов.

```python
@dataclass
class TrainReport:
    step_losses: list[float]
    epoch_losses: list[float]
    validation_losses: list[float]
    grad_norms: list[float]
    fraction_inside_grid: list[float]
    peak_memory_bytes: int
    seconds: float
    optimizer_coverage: dict[str, int]
```

`validation_losses` — функция потерь на валидационной выборке: первое
значение — до первого шага оптимизатора (шаг 0), затем по одному в конце
каждой эпохи, всего `epochs + 1` значений. Если валидационная выборка не
передана (или пуста), список пустой.

`grad_norms` — норма градиента по всем обучаемым параметрам **до** обрезания,
по одному значению на шаг оптимизатора: то, что возвращает
`clip_grad_norm_`. Раньше это значение отбрасывалось. Теперь по нему видно,
как часто срабатывает обрезание с порогом `max_grad_norm` (значения выше
порога) и как меняется масштаб градиента по ходу обучения. Для Muon это
объясняет, почему обрезание на него почти не влияет: ортогонализация
Ньютона–Шульца сама нормирует масштаб обновления. `.item()` вызывается раз на
шаг оптимизатора, а не на батч.

`fraction_inside_grid` — по одному значению на эпоху (среднее доли активаций
в сетке по всем обучающим проходам этой эпохи и по адаптерам; в начале каждой
эпохи накопление сбрасывается, а не тянется со всего прогона), только когда среди
адаптеров модели есть хотя бы один, у которого `mean_fraction_inside_grid()`
возвращает не `None`; для LoRA и DoRA (у которых этот метод не переопределён и
наследуется от `AdapterLinear`, всегда возвращая `None`) список остаётся
пустым (`[]`). `optimizer_coverage` — результат
`OptimizerBundle.coverage()`, показывает, сколько параметров реально досталось
`Muon`, а сколько — запасному `AdamW` (см. `docs/optimizers.md`).

## `set_seed`

```python
def set_seed(seed: int) -> None
```

Задаёт `random`, `numpy` и `torch` (включая `torch.cuda.manual_seed_all`)
одним и тем же значением. Вызывается автоматически в начале `train()`, поэтому
инициализация `DataLoader`-перемешивания воспроизводима по `train_config.seed`.

## `train`

```python
def train(model, dataset, collator, optimizer_config, train_config, device,
          validation_dataset=None) -> TrainReport
```

Порядок действий:

1. `set_seed(train_config.seed)`, модель переводится на `device` и в режим
   `train()`.
2. При `train_config.gradient_checkpointing=True` включается
   `model.gradient_checkpointing_enable()`, затем явно
   `model.enable_input_require_grads()` и `model.config.use_cache = False`
   — чекпоинтинг несовместим с кешем ключей/значений при обучении.
3. `DataLoader` с перемешиванием, детерминированным по тому же `seed`, и
   `collate_fn=collator`.
4. `build_optimizer(model, optimizer_config)` собирает `OptimizerBundle`.
   Ему передаётся сама модель, а не плоский список параметров
   (`model.parameters()`) — `build_optimizer` внутри вызывает
   `split_by_matrix_role(model)`, которой нужен обход `model.named_modules()`,
   чтобы найти внедрённые адаптеры и развести Muon/AdamW по их
   `matrix_parameters()` (см. `docs/optimizers.md`). `PeakMemoryTracker.reset()`
   — до первого шага.
5. Основной цикл по эпохам и батчам: функция потерь модели делится на число
   батчей в её группе накопления (`_group_size`) перед `backward()`, поэтому
   шаг оптимизатора соответствует обучению батчем в `gradient_accumulation`
   раз больше, но не эквивалентен ему в точности: функция потерь модели —
   среднее по токенам внутри одного микробатча, поэтому накопление взвешивает
   микробатчи поровну, а один большой батч взвешивал бы примеры по числу
   токенов. Совпадение точное только при равном числе токенов в микробатчах.
   Для всех методов это одно и то же, так что сравнение методов не
   смещается. Шаг (`clip_grad_norm_` → `step()` → `zero_grad()`) выполняется
   каждые `gradient_accumulation` батчей и дополнительно на последнем батче
   неполного хвоста эпохи (`index == len(loader)`), чтобы накопленный градиент
   неполной группы не терялся. Хвост делится на свою фактическую длину, а не на
   `gradient_accumulation`: иначе последний шаг эпохи получал бы градиент,
   заниженный в `gradient_accumulation / длина хвоста` раз
   (`test_incomplete_accumulation_group_is_divided_by_its_actual_size`). При
   2500 примерах и `gradient_accumulation=8` хвост — 4 батча, то есть раньше
   последний шаг каждой эпохи делался с вдвое меньшим градиентом. Каждые `train_config.log_every` шагов (по
   номеру батча внутри эпохи, `index % log_every == 0`) печатается отдельная
   строка с номером шага и текущей функцией потерь батча — независимо от
   печати по итогам эпохи (см. ниже) и независимо от того, кратен ли шаг
   `gradient_accumulation`.
6. После каждой эпохи — средняя функция потерь по эпохе, средняя доля
   активаций в сетке (`_mean_fraction_inside_grid`) и печать этих значений на
   русском. В начале каждой эпохи цикл вызывает `reset_fraction_inside_grid()`
   на каждом адаптере, поэтому адаптер накапливает сумму и число долей по
   проходам именно этой эпохи (раньше значение перезаписывалось на каждом
   проходе, и в отчёт попадал последний микробатч — по сути один пример).
   Накопление идёт только в режиме `train()`, так что `eval()`-проходы
   (генерация, замер задержки) значение не меняют. `_mean_fraction_inside_grid`
   вызывает `mean_fraction_inside_grid()` полиморфно на каждом адаптере из `adapter_modules(model)`, без проверки
   типа: усредняются только значения, отличные от `None` (их дают только
   `KANLoRALinear`; у LoRA и DoRA — базовая реализация из `AdapterLinear`,
   всегда `None`). Цикл обучения благодаря этому не знает про конкретные
   классы адаптеров.
7. По завершении — время выполнения (`time.perf_counter`) и пиковая
   видеопамять.

## Валидационная функция потерь

Требование учебника (§3.7, с. 96–97) и лекции 5 MLOps («val loss на шаге 0»):
кривая на валидации нужна, чтобы отличить недообучение от переобучения, а
значение на шаге 0 показывает, с чего начинала модель. Источник примеров —
`validation_subsample` (`docs/data.md`): train вне обучающей подвыборки.

- Считается до первого шага (сразу после сборки оптимизатора, модель ещё не
  менялась) и после каждой эпохи — после записи функции потерь эпохи и доли
  активаций в сетке.
- `_validation_loss` переводит модель в `eval()` под `torch.no_grad()`, проходит
  `DataLoader` без перемешивания с тем же `batch_size` и `collator`, что и
  обучение, и возвращает среднее по батчам — так же, как `epoch_losses`.
  Затем исходный режим модели восстанавливается.
- В режиме `eval()` адаптеры не накапливают долю активаций в сетке, поэтому
  `fraction_inside_grid` и `step_losses` с валидацией и без неё совпадают
  (`test_validation_passes_do_not_touch_training_statistics`). Генератор
  случайных чисел валидация всё же потребляет: каждый `iter(DataLoader)` без
  собственного `generator` берёт базовое зерно из глобального генератора
  torch, а у валидационного загрузчика собственного генератора нет. На числа
  обучения это не влияет: у обучающего загрузчика свой генератор с зерном
  `train.seed`, поэтому порядок обучающих батчей не меняется; в Qwen нет
  прореживания (`attention_dropout = 0.0`), а генерация жадная
  (`do_sample=False`).
- Время валидации вычитается из `seconds`: в карточке время обучения остаётся
  сравнимым с прогонами без валидации. Пиковая видеопамять измеряется по всему
  прогону; проход без градиента требует меньше памяти, чем шаг обучения, и пик
  не поднимает.
- Ограничение: KAN-LoRA обновляет наблюдаемый диапазон входа
  (`observed_range`) в любом режиме, поэтому проходы по валидации расширяют
  его так же, как это уже делает генерация на оценке. Отрезок измерения индекса
  нелинейности (`docs/nonlinearity.md`) может стать чуть шире, но пересечение с
  сеткой ограничивает его в любом случае.

## Почему `test_overfits_twenty_examples` размораживает больше, чем адаптеры

Тест использует общую фикстуру `tiny_causal_lm` (`tests/conftest.py`) —
настоящую архитектуру Qwen2, но со случайной инициализацией, крошечным
`hidden_size=32` и `vocab_size=64` при `tie_word_embeddings=True`. При отладке
Задачи 11 выяснилось, что с **полностью замороженной основой** (как это и
делает `inject_adapters` в production-коде: адаптируются только семь целевых
проекций, всё остальное заморожено) функция потерь на этой фикстуре не может
опуститься ниже потолка около 3.5–4.0 — и одинаково для LoRA, DoRA и
KAN-LoRA, при любом ранге адаптера и любой разумной скорости обучения.

Это проверено прямым экспериментом: если вместо адаптеров напрямую разморозить
для обучения ровно те же семь типов проекций (без низкоранговой
реконструкции LoRA/DoRA/KAN-LoRA вообще), потолок получается **тем же самым**
числом с точностью до четырёх знаков. Значит, дело не в математике адаптеров,
а в том, что заморожены `RMSNorm` (масштаб перед каждым под-слоем и перед
`lm_head`) и привязанная (`tie_word_embeddings`) таблица эмбеддингов: `RMSNorm`
фиксирует норму скрытого состояния, из-за чего размороженные проекции не могут
сделать распределение по 64 случайным и плохо разделимым в 32-мерном
пространстве эмбеддингам сколь угодно острым. У настоящей предобученной
модели (`Qwen2.5-Coder-0.5B-Instruct`) эмбеддинги и нормировка уже несут
полезную структуру из предобучения, поэтому в реальных экспериментах это
ограничение не проявляется — оно специфично именно для случайно
инициализированной игрушечной фикстуры.

Поэтому только в этом тесте, поверх адаптеров, дополнительно размораживаются:

- веса `RMSNorm` — функцией `unfreeze_norms(model)` (ищет `"norm"` в имени
  параметра);
- привязанная таблица эмбеддингов — функцией `unfreeze_embeddings(model)`
  (ищет `"embed_tokens"` в имени параметра).

Обе функции определены в `tests/conftest.py`, вызываются только из этого
теста и не используются production-кодом `inject_adapters`: они не меняют
методологию обучения, а лишь снимают искусственный потолок, специфичный для
случайно инициализированной тестовой фикстуры. Скорость обучения в этом тесте
(`0.005`) и число эпох (`150`) тоже подобраны эмпирически ради сходимости за
разумное время (все три метода сходятся к ~0.001 за ~14 секунд суммарно) и не
имеют отношения к гиперпараметрам реальных экспериментов (`2.0e-4`,
зафиксированным в `docs/README.md` и плане).

## `model.enable_input_require_grads()` при чекпоинтинге

При `train_config.gradient_checkpointing=True` рядом с
`model.gradient_checkpointing_enable()` явно вызывается
`model.enable_input_require_grads()` (`train/loop.py`). Причина в том, что
основа модели заморожена, а входные эмбеддинги — первый слой сети — сами по
себе не требуют градиента; без `enable_input_require_grads()`
`torch.utils.checkpoint` может не построить граф автоматического
дифференцирования для checkpoint-сегмента, из-за чего градиент не доходит от
функции потерь до весов адаптера внутри этого сегмента.

Этот вызов — **защита на случай отката/понижения версии `transformers`, а не
исправление бага, воспроизводимого в установленном в репозитории окружении.**
Это подтверждено прямой проверкой (не только чтением кода):

- На `transformers==5.17.0`, установленной в `.venv` этого репозитория,
  `PreTrainedModel.gradient_checkpointing_enable()` уже сама вызывает
  `self.enable_input_require_grads()` безусловно для всех causal LM
  (`self.main_input_name == "input_ids"`). На этой версии обучение адаптера с
  `gradient_checkpointing=True` уже работает корректно даже без явного вызова
  в `train()` — регрессионный тест
  `test_gradient_checkpointing_preserves_adapter_gradient`
  (`tests/train/test_loop.py`) проходит и без патча.
- На нижней границе версии, зафиксированной в `pyproject.toml`
  (`transformers==4.46.0`), тот же код вызывает
  `self.enable_input_require_grads()` только когда
  `self._hf_peft_config_loaded` — то есть только при загрузке адаптеров через
  библиотеку HF PEFT (`get_peft_model`). Адаптеры в этом проекте (LoRA, DoRA,
  KAN-LoRA — `src/kanlora/adapters/`) внедряются собственным кодом
  (`inject_adapters`), а не через HF PEFT, поэтому `_hf_peft_config_loaded`
  никогда не выставляется, и на `transformers==4.46.0` без явного вызова
  обучение с `gradient_checkpointing=True` действительно падает: проверено
  прямым запуском обучения тестовой модели с `LoRA`-адаптером в изолированном
  окружении с `transformers==4.46.0` — без патча `backward()` кидает
  `RuntimeError: element 0 of tensors does not require grad and does not have
  a grad_fn`; с явным `model.enable_input_require_grads()` градиент доходит до
  `lora_b`, и обучение проходит как обычно.

Итог: баг реален на нижней границе поддерживаемых версий `transformers`, но
уже не воспроизводится на версии, установленной в текущем окружении, — апстрим
перестал требовать HF PEFT для этого условия. Явный вызов оставлен, чтобы
поведение не зависело от конкретной установленной версии зависимости.

## Проверенные инварианты

- При `gradient_checkpointing=True` градиент доходит до адаптера так же, как и
  без чекпоинтинга: `lora_b` меняется, функция потерь падает
  (`test_gradient_checkpointing_preserves_adapter_gradient`).
- Все три метода адаптации переобучивают двадцать примеров почти до нулевой
  функции потерь (`test_overfits_twenty_examples`, с размороженными нормой и
  эмбеддингами — см. выше).
- Обучаются только параметры с `requires_grad=True`; замороженная основа не
  меняется ни на бит (`test_only_adapter_parameters_change`).
- Доля активаций в сетке логируется по одному значению на эпоху для KAN-LoRA
  (`test_reports_fraction_inside_grid_per_epoch`); это среднее за эпоху по
  всем проходам, а не значение последнего микробатча
  (`test_fraction_inside_grid_is_the_epoch_mean_not_the_last_microbatch`,
  `tests/adapters/test_kan_lora.py`: среднее, сброс, непопадание
  `eval()`-проходов); остаётся пустым списком
  для линейных методов (`test_linear_methods_report_no_grid_statistics`).
- Накопление градиента даёт тот же результат, что и эквивалентно больший
  батч без накопления, с точностью до `rel=1e-3`
  (`test_gradient_accumulation_matches_the_larger_batch`) — забытое деление на
  число накоплений завысило бы эффективный шаг оптимизатора незаметно для
  любого другого теста.
- Отчёт несёт время выполнения, покрытие оптимизатора и (на CPU — честно
  нулевую) пиковую память (`test_report_carries_timing_memory_and_coverage`).
- Построчный лог печатается каждые `log_every` шагов и ни разу между ними
  (`test_logs_loss_every_log_every_steps`).
- `PeakMemoryTracker` возвращает `0` на CPU и идемпотентен при повторном
  `reset()` (`test_reports_zero_on_cpu`, `test_reset_is_idempotent_on_cpu`); на
  CUDA действительно отслеживает рост выделенной памяти
  (`test_tracks_allocation_growth_on_cuda`, пропускается без GPU).
