# Цикл обучения и замер видеопамяти (`train/loop.py`, `train/memory.py`)

**Модули:** `src/kanlora/train/loop.py`, `src/kanlora/train/memory.py`
**Тесты:** `tests/train/test_loop.py`, `tests/train/test_memory.py`

## Зачем один цикл на все три метода

`train()` — единственная функция, которая обучает модель, независимо от того,
какой адаптер в неё внедрён (`inject_adapters` из `kanlora.adapters.inject`).
Причина та же, что и у единого внедрителя адаптеров и единой разводки по
оптимизаторам: если бы LoRA, DoRA и KAN-LoRA обучались разным кодом, различие
в реализации циклов просочилось бы в сравнение методов, не выдав ошибки.

Сходимость самого цикла юнит-тестом в общем виде не проверяется — вместо
этого используется **переобучение двадцати примеров**: функция потерь обязана
упасть почти до нуля (`test_overfits_twenty_examples`). Такой тест ловит
подавляющее большинство ошибок цикла — неверную маску, оторванный граф
градиентов, замороженные не те параметры — ни одна из которых не даёт
исключения сама по себе, а незаметно портит качество итоговой модели.

## `PeakMemoryTracker`

```python
class PeakMemoryTracker:
    def __init__(self, device: torch.device) -> None: ...
    def reset(self) -> None: ...
    def peak_bytes(self) -> int: ...
```

Обёртка над `torch.cuda.max_memory_allocated`. На CPU (`device.type != "cuda"`)
`reset()` — не-операция, а `peak_bytes()` всегда возвращает `0`: карточка
результата эксперимента тогда честно показывает, что замера не было, а не
подставляет случайное или нулевое значение по совпадению.

Величина сравнима между LoRA, DoRA и KAN-LoRA только при жёстко одинаковых
длине последовательности, размере батча и точности (fp32) для всех трёх —
замер вынесен одним общим куском кода намеренно, чтобы «удобная» правка под
один метод не разошлась незаметно с остальными.

## `TrainConfig` и `TrainReport`

```python
@dataclass(frozen=True)
class TrainConfig:
    epochs: int = 2
    batch_size: int = 1
    gradient_accumulation: int = 8
    seed: int = 0
    gradient_checkpointing: bool = True
    log_every: int = 20
```

Нормы обрезания градиента в `TrainConfig` намеренно нет — она хранится только
в `OptimizerConfig` (`train/optimizers.py`) и берётся циклом оттуда. Если бы
одно и то же значение можно было задать в двух местах, они могли бы разойтись
молча и незаметно изменить методологию для части прогонов.

```python
@dataclass
class TrainReport:
    step_losses: list[float]
    epoch_losses: list[float]
    fraction_inside_grid: list[float]
    peak_memory_bytes: int
    seconds: float
    optimizer_coverage: dict[str, int]
```

`fraction_inside_grid` — по одному значению на эпоху, только когда среди
адаптеров модели есть хотя бы один `KANLoRALinear`; для LoRA и DoRA список
остаётся пустым (`[]`). `optimizer_coverage` — результат
`OptimizerBundle.coverage()`, показывает, сколько параметров реально досталось
`Muon`, а сколько — запасному `AdamW` (см. `docs/optimizers.md`).

## `set_seed`

```python
def set_seed(seed: int) -> None
```

Задаёт `random`, `numpy` и `torch` (включая `torch.cuda.manual_seed_all`)
одним и тем же значением. Вызывается автоматически в начале `train()`, поэтому
инициализация `DataLoader`-перемешивания воспроизводима по `train_config.seed`.

## `train`

```python
def train(model, dataset, collator, optimizer_config, train_config, device) -> TrainReport
```

Порядок действий:

1. `set_seed(train_config.seed)`, модель переводится на `device` и в режим
   `train()`.
2. При `train_config.gradient_checkpointing=True` включается
   `model.gradient_checkpointing_enable()` и `model.config.use_cache = False`
   — чекпоинтинг несовместим с кешем ключей/значений при обучении.
3. `DataLoader` с перемешиванием, детерминированным по тому же `seed`, и
   `collate_fn=collator`.
4. `build_optimizer` собирает `OptimizerBundle` по `optimizer_config`;
   `PeakMemoryTracker.reset()` — до первого шага.
5. Основной цикл по эпохам и батчам: функция потерь модели делится на
   `train_config.gradient_accumulation` перед `backward()`, поэтому шаг
   оптимизатора эквивалентен обучению батчем в `gradient_accumulation` раз
   больше. Шаг (`clip_grad_norm_` → `step()` → `zero_grad()`) выполняется
   каждые `gradient_accumulation` батчей и дополнительно на последнем батче
   неполного хвоста эпохи (`index == len(loader)`), чтобы накопленный градиент
   неполной группы не терялся.
6. После каждой эпохи — средняя функция потерь по эпохе, средняя доля
   активаций в сетке по всем `KANLoRALinear` (`_mean_fraction_inside_grid`,
   если такие адаптеры есть) и печать этих значений на русском.
7. По завершении — время выполнения (`time.perf_counter`) и пиковая
   видеопамять.

## Почему `test_overfits_twenty_examples` размораживает больше, чем адаптеры

Тест использует общую фикстуру `tiny_causal_lm` (`tests/conftest.py`) —
настоящую архитектуру Qwen2, но со случайной инициализацией, крошечным
`hidden_size=32` и `vocab_size=64` при `tie_word_embeddings=True`. При отладке
Задачи 11 выяснилось, что с **полностью замороженной основой** (как это и
делает `inject_adapters` в production-коде: адаптируются только семь целевых
проекций, всё остальное заморожено) функция потерь на этой фикстуре не может
опуститься ниже потолка около 3.5–4.0 — и одинаково для LoRA, DoRA и
KAN-LoRA, при любом ранге адаптера и любой разумной скорости обучения.

Это проверено прямым экспериментом: если вместо адаптеров напрямую разморозить
для обучения ровно те же семь типов проекций (без низкоранговой
реконструкции LoRA/DoRA/KAN-LoRA вообще), потолок получается **тем же самым**
числом с точностью до четырёх знаков. Значит, дело не в математике адаптеров,
а в том, что заморожены `RMSNorm` (масштаб перед каждым под-слоем и перед
`lm_head`) и привязанная (`tie_word_embeddings`) таблица эмбеддингов: `RMSNorm`
фиксирует норму скрытого состояния, из-за чего размороженные проекции не могут
сделать распределение по 64 случайным и плохо разделимым в 32-мерном
пространстве эмбеддингам сколь угодно острым. У настоящей предобученной
модели (`Qwen2.5-Coder-0.5B-Instruct`) эмбеддинги и нормировка уже несут
полезную структуру из предобучения, поэтому в реальных экспериментах это
ограничение не проявляется — оно специфично именно для случайно
инициализированной игрушечной фикстуры.

Поэтому только в этом тесте, поверх адаптеров, дополнительно размораживаются:

- веса `RMSNorm` — функцией `unfreeze_norms(model)` (ищет `"norm"` в имени
  параметра);
- привязанная таблица эмбеддингов — функцией `unfreeze_embeddings(model)`
  (ищет `"embed_tokens"` в имени параметра).

Обе функции определены в `tests/conftest.py`, вызываются только из этого
теста и не используются production-кодом `inject_adapters`: они не меняют
методологию обучения, а лишь снимают искусственный потолок, специфичный для
случайно инициализированной тестовой фикстуры. Скорость обучения в этом тесте
(`0.005`) и число эпох (`150`) тоже подобраны эмпирически ради сходимости за
разумное время (все три метода сходятся к ~0.001 за ~14 секунд суммарно) и не
имеют отношения к гиперпараметрам реальных экспериментов (`2.0e-4`,
зафиксированным в `docs/README.md` и плане).

## Проверенные инварианты

- Все три метода адаптации переобучивают двадцать примеров почти до нулевой
  функции потерь (`test_overfits_twenty_examples`, с размороженными нормой и
  эмбеддингами — см. выше).
- Обучаются только параметры с `requires_grad=True`; замороженная основа не
  меняется ни на бит (`test_only_adapter_parameters_change`).
- Доля активаций в сетке логируется по одному значению на эпоху для KAN-LoRA
  (`test_reports_fraction_inside_grid_per_epoch`) и остаётся пустым списком
  для линейных методов (`test_linear_methods_report_no_grid_statistics`).
- Накопление градиента даёт тот же результат, что и эквивалентно больший
  батч без накопления, с точностью до `rel=1e-3`
  (`test_gradient_accumulation_matches_the_larger_batch`) — забытое деление на
  число накоплений завысило бы эффективный шаг оптимизатора незаметно для
  любого другого теста.
- Отчёт несёт время выполнения, покрытие оптимизатора и (на CPU — честно
  нулевую) пиковую память (`test_report_carries_timing_memory_and_coverage`).
- `PeakMemoryTracker` возвращает `0` на CPU и идемпотентен при повторном
  `reset()` (`test_reports_zero_on_cpu`, `test_reset_is_idempotent_on_cpu`); на
  CUDA действительно отслеживает рост выделенной памяти
  (`test_tracks_allocation_growth_on_cuda`, пропускается без GPU).

## Не реализовано

Сборка конфигурации и карточки результата прогона — задача 16 плана, ещё не
сделана. Генерация SQL реализована (`eval/generate.py`, `docs/generate.md`,
Задача 12), метрики оценки и мера выученной нелинейности — тоже
(`docs/exact_match.md`, `docs/execution.md`, `docs/nonlinearity.md`).
`train()` спроектирован под них: `model` после `train()` содержит обученные
адаптеры в том же объекте, который передаётся дальше в генерацию, оценку и
анализ нелинейности без дополнительного связывания.
