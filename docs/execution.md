# Execution Accuracy (`eval/execution.py`)

**Модуль:** `src/kanlora/eval/execution.py`
**Тесты:** `tests/eval/test_execution.py`

## Зачем метрика нужна отдельно от Exact Match

[`exact_match.md`](exact_match.md) сравнивает разобранные SQL-деревья:
запрос, написанный иначе, но синтаксически эквивалентный, засчитывается,
а запрос с другой структурой, но тем же результатом — нет (например,
`WHERE price > 15` и `WHERE NOT price <= 15`). Execution Accuracy закрывает
этот случай: запрос исполняется на настоящей базе `.sqlite`, и сравниваются
**результаты**, а не текст и не разобранное дерево. Это делает метрику
терпимее к переформулировкам и одновременно уязвимее к случайным
совпадениям результата у семантически разных запросов — поэтому в работе
приводятся обе метрики, а не одна вместо другой.

## `ExecutionOutcome` и `execute_query`

```python
@dataclass(frozen=True)
class ExecutionOutcome:
    rows: list[tuple] | None
    failed: bool
    data_error: bool = False

def execute_query(db_path: Path, query: str, timeout: float = 30.0) -> ExecutionOutcome
```

Любая ошибка — отсутствующий файл базы, синтаксическая ошибка в SQL,
превышение таймаута — превращается в `ExecutionOutcome(None, True)`, а не в исключение.
Причина: модель регулярно генерирует неисполнимый текст, и это ожидаемая,
частая часть измерения, а не аварийная ситуация, которая должна остановить
оценку всего прогона (тот же принцип, что и у обработки ошибок разбора
в `exact_match_by_hardness`).

Подключение открывается в режиме только для чтения (`mode=ro` в URI
`sqlite3.connect`), поэтому сгенерированный моделью SQL не может изменить
файл базы данных на диске, даже если это `UPDATE`/`DELETE`/`DROP`.
`text_factory` декодирует текстовые столбцы в UTF-8 с заменой
недекодируемых байт, а не падает на них — базы PAUQ русскоязычные, и
байтовый мусор в отдельной строке не должен обрушивать исполнение всего
запроса.

### Таймаут исполнения

Параметр `timeout` (по умолчанию `30.0` секунд) используется дважды. Во-первых,
как аргумент `sqlite3.connect(timeout=...)`: это только время ожидания
блокировки файла базы и на длительность самого запроса оно не влияет. Во-вторых,
и именно это ограничивает время исполнения, как дедлайн по `time.monotonic()`:
после подключения вызывается `connection.set_progress_handler(...)`, и
обработчик, срабатывающий каждые 1000 инструкций виртуальной машины sqlite
(`_PROGRESS_STEP`), возвращает ненулевое значение, когда дедлайн прошёл.
Дедлайн задаётся до `connection.execute`. `sqlite3.connect` блокировку не
берёт, поэтому ожидание блокировки (busy timeout) происходит внутри
`execute`, в том же окне, что и дедлайн исполнения. Худший случай —
примерно `timeout` плюс непрерываемый отрезок: до `_PROGRESS_STEP` (1000)
инструкций виртуальной машины между вызовами обработчика плюс одна долгая
инструкция, а не сумма двух ожиданий. По истечении дедлайна
sqlite прерывает запрос ошибкой `interrupted`, и `execute_query` возвращает
`ExecutionOutcome(None, True)`; для предсказания это промах, для эталона — ошибка данных. Так декартово произведение или бесконечный рекурсивный CTE из ответа
модели не подвешивает оценку. Новых параметров или значений по умолчанию не
вводилось: используется то же `timeout=30.0`. Обработчик снимается
(`set_progress_handler(None, 0)`), а соединение закрывается в блоке `finally` на
всех путях. Дедлайн нестрогий: обработчик вызывается между инструкциями
виртуальной машины, и одна долгая инструкция, например сортировка большой
промежуточной таблицы, до конца не прерывается.

## `results_match` и роль `ORDER BY`

```python
def results_match(gold: ExecutionOutcome, predicted: ExecutionOutcome, order_matters: bool) -> bool
```

Если хотя бы одно исполнение помечено `failed`, совпадения нет — сравнивать
`None` с чем бы то ни было бессмысленно, и промах гарантированно не должен
засчитываться как успех. Иначе: при `order_matters=True` строки сравниваются
позиционно (`gold.rows == predicted.rows`), при `order_matters=False` —
как мультимножества через сортировку `repr` каждой строки. Разница
принципиальна: SQL без `ORDER BY` не гарантирует никакого порядка строк, и
требование его совпадения занижало бы метрику по признаку, не имеющему
отношения к правильности запроса.

Сравнение через `repr` различает `20` и `20.0`, а официальный test-suite
сравнивает значения через `==`. Расхождение возможно, когда эталон и ответ
получают одно число выражениями разного типа (например, `AVG` против
целого). Оно одинаково для всех методов и сравнения методов не искажает.
Позиционное сравнение при `order_matters=True` идёт через `==`, поэтому
там `20` и `20.0` совпадают, и расхождение относится только к ветви без
`ORDER BY`.

## `execution_accuracy`

```python
def execution_accuracy(
    gold: list[str], predicted: list[str], db_ids: list[str], root: Path, layout: DatasetLayout,
) -> float
```

Для каждой тройки (эталон, предсказание, `db_id`) путь к файлу базы строится
через `database_path(root, layout, db_id)` из `kanlora.data.loaders`
(`docs/data.md`) — та же раскладка, что используют загрузчики Spider и PAUQ,
поэтому метрика не заводит собственное представление о структуре каталогов
набора. Требование к `ORDER BY` берётся из **эталонного** запроса
(`"order by" in gold_query.lower()`), а не из предсказанного: предсказание
может как включать, так и опускать `ORDER BY` по своей структуре, и это не
должно определять, что именно с ним сравнивается.

Итоговая оценка — доля совпавших пар. Несовпадение длин `gold`/`predicted`/
`db_ids` — `ValueError`, а не тихое усечение по меньшей длине, по тому же
принципу, что и в `exact_match`/`exact_match_by_hardness`.

## Проверка данных и область применения

EA сравнивает результаты на одной SQLite-базе для каждого примера, а не на
множестве вариантов базы. Для итоговой оценки необходимы все базы и все
исполнимые эталоны полного dev соответствующего набора. Для PAUQ используются
только его собственные локализованные базы и раскладка, без подстановки Spider.

`validate_execution_data` проверяет каждый эталон до загрузки модели. Отсутствие
файла, повреждение базы, ошибка SQL или таймаут эталона вызывают
`EvaluationDataError` с `db_id` и причиной. При вычислении EA эталон проверяется
повторно: поздняя ошибка данных также не становится промахом. Ошибка SQL предсказания остаётся промахом; ошибки SQLite при открытии,
чтении, повреждении или недоступности файла классифицируются как ошибки данных
даже при исполнении предсказания. В final и pilot ошибка данных останавливает
прогон; в smoke допускается `execution_accuracy: null` с непустым полем
`execution_accuracy_reason`. При успешной оценке причина равна `null`.

Это изменение методики: прежние значения на неполных данных несопоставимы;
перед сравнением необходимо повторить все затронутые ячейки матрицы.
